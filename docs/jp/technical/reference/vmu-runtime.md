# VMUランタイム

[日本語ドキュメント](../../README.md) | [English](../../../en/technical/reference/vmu-runtime.md) | [リング・りんぐ・ランドのRAM](ring-ring-land-ram.md) | [セーブファイルの形式](save-file.md)

リング・りんぐ・ランドのVMU版は、LC86Kのアセンブリで書いた小さなランタイムの上で動きます。
ランタイムは、VMU向けに書き直したCが使うインターフェース `pocketstation/src/vmu/vmu_hw.h` を、本物のVMUのタイマー、ボタン、画面、フラッシュの上で提供します。
このページはランタイムのリファレンスです。
呼び出し方、状態の置き場所、イベントの順番の決め方、テスト用ハーネスが模すBIOSの範囲を説明します。

ソースは `pocketstation/src/vmu_rt/` にあります。
その `test/` フォルダーの `rt_test.s` は、共通のシナリオ（`pocketstation/tests/scenarios/*.scn`）を実行するテスト用のGAMEです。
同じシナリオは、インターフェースのCモデル `vmu_host.c` の上でも `scenario_host` として実行します。
`pocketstation/tests/test_runtime.py` は、2つのイベントログが1行ずつ一致することを確かめます。
ランタイムはまだハーネスの上でしか動かしていません。
本物のVMUでの最初のテストは、ドリームキャストへのインストールのマイルストーンで行います。

## クロック

BIOSはGAMEを32 kHzの水晶発振器で起動します。
ランタイムはリセット時に、ドリームキャストにつながないVMUで使える最速の設定である、6 MHzのCF発振器の6分周に切り替えます。
命令サイクルは1マイクロ秒になるので、ゲームの1フレーム（30.76 ms、32.5 Hz）は約30,760サイクルです。
公開資料がドリームキャストにつながないVMU向けに勧めるRC発振器では、1フレームが1,500〜2,250サイクルにしかなりません。

## 呼び出し規約

- どのルーチンも `CALLF` で呼びます。
  引数はACC、B、Cと16ビットの組TRH:TRLで渡します。
  結果はACCで返り、割り込みラインのマスクはTRH:TRLで返ります。
  ソースの各ルーチンのヘッダーに、ほかに壊すレジスターが書いてあり、下の表にも載せています。
- RAMバンク1を常に選んでおきます（PSW `0x02`）。
  割り込みルーチンがこれを前提にするので、バンク0に切り替えるコードは先に割り込みを止めます。
- スタックはBIOSが設定するとおり、バンク0の `0x80` からです。
- 割り込みも触る状態を扱うルーチンは、IEのビット7を落とし、終わるとIEを元に戻します。
  ゲームの割り込みハンドラーは、`rt_idle` から割り込みを止めた状態で呼ばれます。
- 割り込みルーチンはすべてのレジスターを保ちます。

## GAMEが用意するもの

`rt_test.s` が手本です。
ランタイムの上に作るGAMEは、次のことを守ります。

- ほかの何よりも先に `sfr.inc`、`rt.inc`、続いて `rt_vectors.s` を取り込みます。
  `rt_vectors.s` は `0x000`〜`0x1F5` を埋めます。
  ベクター、リセットの処理、そして `0x100`〜`0x1F5` にBIOSが戻ってくるスタブとトランポリンです。
  ここにはほかに何も置けません。
- `0x200` にVMSヘッダーを置き、パレットとアイコンを続けます。
  アイコンが1つなら `0x480` で終わり、アイコンが1つ増えるごとに `0x200` ずつ延びます。
- ランタイムの残り（`rt_ram.s`、`rt_events.s`、`rt_input.s`、`rt_lcd.s`、`rt_file.s`、`rt_sound.s`、`rt_power.s`）は、アイコンより後のどこに取り込んでもかまいません。
- `app_main` を定義します。
  リセットはRAMを消してスケジューラーを動かしてから、これを呼びます。
  戻るとVMUはそのまま停止します。
- `app_tables` を用意します。`rt_rom8` はPocketStationのファイルのオフセットをこのラベルに足して読みます（[表](#表)）。

`rt_set_handler` で設定したハンドラーは、割り込みを止めた状態で動きます。
Timer 0は取り込んでいないオーバーフローを1つしか持てません。
そのため、ハンドラーや割り込みを止めた区間がTimer 0の1区間より長く続くと、2つ目以降のオーバーフローが失われ、スケジューラーが実時間より遅れます。

## メモリー

| 場所 | バイト数 | 中身 |
|---|---|---|
| バンク1 `0x00`〜`0x1F` | 32 | `rt_reserved`。`0x00`〜`0x03` に間接アドレスレジスターR0〜R3、その後にスケジューラーのカウント、状態、ラインのマスク |
| バンク1 `0x20`〜`0xF8` | 217 | 直接アドレス指定する、ゲームの使用頻度の高い項目 |
| バンク1 `0xF9`〜`0xFF` | 7 | `rt_input`。押されているボタン、離すまで離したと読むボタン、スリープ、終了、LCDのフラグ（使うのは3バイト） |
| WRAM `0x000`〜`0x1E7` | 488 | ゲームのそのほかの項目。`rt_r8` と `rt_w8` で読み書きする |
| WRAM `0x1E8`〜`0x1FF` | 24 | `rt_save`。ペットのセーブのセクター数、セクター0のパッケージ内のページ、チェーンの最初の88ブロックのうち4ブロックごとの1つ。リセット時に一度だけ探す |
| バンク0の `0x80` から | | スタック |
| XRAM | 192 | 画面。ゲームが直接描く |

ゲームの項目は `vmu_ram` のオフセットを持ち、[リング・りんぐ・ランドのRAM](ring-ring-land-ram.md)のページがその地図です。
`0x100` より下のオフセットはバンク1の同じアドレス、残りはオフセットから `0x100` を引いたWRAMのアドレスです。
`vmu_ram` の32バイトのスタック用の予備は、VMUには別に持ちません。

ACCで値を返さないルーチンはACCを壊します。
ただし `rt_w8`、`rt_present`、`rt_lcd` はACCを保ちます。
ラインは `vmu_hw.h` のものです。
ボタン `0x001F`、ティック `0x0100`、RTC `0x0200`、ドック `0x0400`、サウンド `0x2000` です。

フレームバッファーは、画面に出るとおりVMUのバイト順でXRAMに置きます。
バンク0に0〜15行、バンク1に16〜31行があり、6バイトの行が2つ続いた後に4バイトの隙間があります。
`rt_fb_row` が行の場所を返し、ゲームはR2かR3を通して書きます。
XRAMの行がそのまま画面なので、`rt_present` はハーネスのためにフレームの印を付けるだけです。

## スケジューラー

各イベントがいつ起きるかはタイマーのカウントで `vmu_host.c` が決めていて、ランタイムはその計算をそのまま移しています。

- ティックモードの周期はリロード値に1を足したものです。
  フレームモードと高速モードで15,626カウント、スタンバイで1,954カウントです。
- サウンドは（サンプル数 + 1）×（1サンプルのカウント + 1）カウントで終わります。
  1サンプルは低速で501カウント、高速で72カウントです。
- RTCは現在のクロックの半周期ごとに反転します。
  ランチャーのクロックで999,424カウント、フレームモードで253,952カウントです。
- 同じカウントに重なったイベントは一緒に起きます。
  サウンドの終わりが先で、ティックとRTCは1回のハンドラー呼び出しにまとまります。

順番はソフトウェアで計算し、ハードウェアのタイマーからは取りません。

- `rt_idle` は1回の呼び出しでちょうど1つのイベントを取ります。
  一番近いイベントを計算し、Timer 0がそこまで進むまで停止して、そのイベントを進め、有効なラインがラッチされている間ハンドラーを呼びます。
- Timer 0は経過時間を計るだけです。
  オーバーフローのたびに周期の数をカウントに足し（1周期32カウント、スタンバイで使う最も遅いクロック2では16カウント）、停止を起こします。
  イベントを起こすことはないので、ゲームが遅れても順番は常にホストと同じです。
- 取り込む前にオーバーフローが来ても、経過したカウントは失われません。
  再始動は、取り込んでいないオーバーフローのリロード分の周期を経過に足します。
  イベントがすでに予定の時刻を過ぎていれば、その区間をすぐに足し、残りを次の区間に持ち越します。
- ティックモードを始めるか変えるとき、ランタイムは時間を失わないよう、Timer 0の周期の区切りを最大1周期待ちます。
  フレームモードでは最大63サイクルです。

## ボタン、スリープ、モード

- ボタンは、`rt_idle` が起きるたび、ベースタイマーの割り込みで1秒に2回、待ち受けているラインが押されたときのポート3の割り込みで読みます。
  ポート3が変わっていなければ、読み取りはすぐに戻ります。
- スリープはゲームからは見えません。
  `rt_idle` は進んだカウントを保ったままTimer 0を止め、LCDを消し、もう一度スリープが押されるまで停止します。
  その後LCDを戻し、止めたところからスケジュールを再開します。
  起きたときに押されていたボタンは、離すまで離したと読むので、ゲームには押し直してから見えます。
- モードはゲームを終わらせません。
  `VMU_SYS_QUIT` を立て、次の `rt_sys_flags` の読み取りが一度だけそれを返して消し、どうするかはゲームが決めます。
- ドックのラインはINT0を通してポート7に従います。

## BIOSの呼び出しとペットのセーブ

ランタイムは、GAMEの最初の512バイトの決まったアドレスにある入り口を通してBIOSを呼びます。

| GAMEのアドレス | 呼ぶもの | 用途 |
|---|---|---|
| `0x0100` | FM_WRT_EX（ROM `0x0100`） | （使わない。`0x0105` のRETにページ書き込みが戻る） |
| `0x0110` | FM_VRF_EX（ROM `0x0110`） | 書いたセーブのページの照合 |
| `0x0120` | FM_PRD_EX（ROM `0x0120`） | ディレクトリー、セーブ、CRCを持つヘッダーのページの読み取り |
| `0x0130` | TIMER_EX（ROM `0x0130`） | ベースタイマーの割り込みごとのBIOSの時計 |
| `0x0150` | ROM `0xE024` のページ書き込み | セーブのページの書き込み |
| `0x01F0` | モードの切り替え（ROM `0x01F0`） | ゲームの終了 |

ペットのセーブは、ドリームキャスト版がペットを送るときに書く `BASLUSP01013` です。
ドリームキャスト版はPS1のファイルの最初の `0x400` バイトだけを圧縮せずに持ちます。CARDAはそこより後ろを読まず、ゲームのペットのセクターはセクター6だからです。残りはゼロとして読み戻します。ほかのセーブはすべて圧縮します。
ドリームキャスト版が読み戻せるよう有効なパッケージのまま保つ必要があるので、ランタイムはMapleのブロック書き込みコマンドが使う、BIOS自身のページ書き込みで書きます。
FM_WRT_EXはデータファイルが置かれるフラッシュのバンク1を拒みますが、`0xE024` のページ書き込みはどちらのバンクも受け付けます。
入り口が戻り先としてROM `0x0103` を積むので、ページ書き込みのRETはFM_WRT_EXの末尾を通って `0x0105` でGAMEに戻ります。
各セクターの書き込みはFM_VRF_EXで照合します。
その後ランタイムはパッケージのCRC（`vmu_image.vms_crc` と同じXMODEM）を更新し、それを持つヘッダーのページを同じ方法で書きます。

CRCはパッケージ全体にかかります。細いペットのセーブでは5ブロックです。
ランタイムはセクター数をチェーンの最初の22ブロックまでに抑え、CRCを計算し直さず、ヘッダーにあるCRCを補正します。
初期値0のXMODEMは線形です。

1. ページ書き込みの前、ページバッファーに新しいページがある間に、古いページをLDFで読み、古いページと新しいページのXORのCRCを取ります。
2. それに、多項式を法としてx^(1024 N)を掛けます。Nは書いたページより後ろにあるパッケージのページ数です。係数はNのビットごとに1つ、16個の表 `rt_crc_pow` から取ります。
3. その結果をヘッダーが持つCRCにXORします。

もともとCRCが正しくないパッケージは、正しくないままです。
GAMEからのLDFは実機でまだ確かめていません。最初の実機での実行はR3b-4です。

セーブは、ハーネスの約9,900サイクル（1 MHzで10ミリ秒）割り込みを止めます。
これにハーネスが数えないBIOSの呼び出しが加わります。ページ書き込み2回、FM_VRF_EX 2回、FM_PRD_EX 2回です。
その間のTimer 0のオーバーフローは最初の1回を除いて失われるので、スケジュールの進みがその分遅れます。
イベントの順番は変わりません。

## 表

リング・りんぐ・ランドの表は、PocketStationのファイルの `0x4A00`〜`0xA9FF` の96ページです。
ビルドのときに `RES1506.BIN` から作り、GAMEのフラッシュに `app_tb_pages` として持ちます。
`app_tables` は `app_tb_pages - 0x4A00` なので、`rt_rom8` はファイルのオフセット `off` を `app_tables + off` からLDCで読みます。
ページ `PP` ごとに `app_tb_PP` もあり、`app_tb_PP + off` で同じ並びのどのオフセットも読めます。`app_hi` は `app_tb_9D` です。
ポインターからオフセットを作るコードは `app_tb_map` でGAMEの中の場所を引きます（`g_tb_find`）。
ペットのセーブがなければ、GAMEは何も描かずに `rt_power` で終わります。

## デバッグ用のポート

どのVMUも使わない3つのSFRで、ランタイムはハーネスに動作を伝えます。
実機はこの書き込みを無視します。

| SFR | 名前 | 書き込みの意味 |
|---|---|---|
| `0x16D` | `RT_IDLE_MARK` | `rt_idle` の呼び出しが始まった。ハーネスは入力イベントをこれで数える |
| `0x16E` | `RT_LOG` | ハーネスの `--log` に書く1バイト（テスト用GAMEのイベントログ） |
| `0x16F` | `RT_PRESENT_PORT` | フレームを表示した。ハーネスは状態を書き出し、スクリプトを進める |

## ハーネス

`pocketstation/harness/vmu_harness.c` は、取り込んだLC86Kのコア（Dmitry GrinbergのVMUエミュレーターの `cpu.c`、BSD-3）の上で、128 KBのフラッシュイメージからGAMEを動かします。
BIOSのコードは実行しません。
上の表のROMの入り口 `0x0100`、`0x0110`、`0x0120`、`0x0130`、`0xE024` と、`0x01F0` の終了を、北米版BIOSの逆アセンブルから模します。
フラッシュのルーチンの後は、BIOSのルーチンが壊すレジスターすべてに `0xA5` を残すので、呼び出しをまたいで値を保つことに頼るコードは、VMUと同じように失敗します。
TIMER_EXはすべてのレジスターを保ちます。
ほかのROMの入り口に入るか、ページ書き込みが知らないアドレスに戻ると、実行を止めます。
BIOSのGAMEの起動も模します。
バンク0 `0x6D` のブロック数、OCR `0xA3`、SP `0x7F`、RAMバンク1です。

アイドルのスケジュールでは、停止したCPUを次のタイマーのイベントまで一気に進めます。
実時間のスケジュールでは、すべてのサイクルを実行します。
`--report --map GAME.map` を付けると、表示から次の表示までのフレームについて次のように出力します。

```
frames 299 period 30766
cycles/frame mean 3262 p90 3265 max 3634 frame 132
runtime cycles/frame mean 2053 max 2424
ticks 286 late max 73 cycles
counts drift min -5 max 13
missed ticks 0 (overrun 0, late 0)
```

- periodはサイクル単位のティックの周期です。
  ランタイムの状態から読んだティックモードのリロード値に1を足したカウント数に、そのモードのクロックでの1カウントのサイクル数を掛けたものです。
- サイクルはCPUが実行したもので、停止中は除きます。
- ランタイムの分は、ランタイムのラベル（`rt_` で始まり、`rt_test` でないもの）の範囲のアドレスで実行したサイクルです。
  Waterbearはマップを出力しないので、そのアドレスのリンクマップは `pocketstation/tools/vmu_map.py` が書きます。
- 落としたティックは2種類です。
  1つは超過（overrun）で、実行時間がティックの周期より長かったフレームです。
  もう1つは遅れ（late）で、予定の時刻とそれを取る `rt_idle` の呼び出しの開始の、遅いほうからTimer 0の2周期より後に `rt_idle` が取ったティックです。
  ゲームの次のアイドルを待つのはホストと同じ動きで、遅れではありません。
  モードの開始後の最初のティックが予定の時刻を決め、以降は1周期ずつ進みます。
  スリープ中の時間とモードの切り替えは予定の時刻をずらします。
- counts driftは、各 `rt_ev_step` で、ランタイムが進めて持つカウントがTimer 0の実際に進んだカウントからどれだけずれているかを、最初の時点からの差で示します。
